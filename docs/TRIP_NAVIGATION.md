# Journey map, pickup and drop-off

Starting a trip now saves the ordered planned stops and opens `/trips/{ride}/map`. Confirmed passengers reach their own map from Find Ride or their booking. Existing trips without a snapshot derive their ordered stops from the saved locations. Install only `2026_10_30_010000_add_trip_navigation.php`; its nullable fields do not start or complete any real trip.

The driver's map shows all ordered stops. **Passenger on board** records the next pickup; **Confirm passenger drop-off** records the next drop-off. A shared destination drops off the accepted group together. These are deliberate driver confirmations, not assumptions based on GPS proximity. Out-of-order actions are rejected, repeated actions do not advance another passenger, and completed trips reject new stop actions. Stop confirmations use authenticated, CSRF-protected POSTs. The normal complete-trip action remains available on the driver schedule and records the existing carbon report.

Live movement reads the existing GPS cache. The marker animates between newly received fixes; when close enough to the planned road it interpolates along the route. It does not extrapolate beyond the last fix. Stale/paused/missing GPS is labelled and movement stops; completion clears location. The upload token is never included in participant responses. Only the owning driver and accepted passengers may open the map or GPS feed. Passenger maps contain their own pickup/drop-off pins and the driver's position, not other passengers' names or pickup pins. Shared detours may therefore differ from the passenger's displayed direct route estimate.

Navigation is live only. Only `in_progress` trips may render the map; scheduled, completed or cancelled map URLs return to the user's ride list. A completed feed returns only an end signal and return URL, with no route stops or location. An already-open map removes its layers, stops animation and returns to bookings/schedule. Browser-back restoration revalidates with the server. Tracking links appear only during active trips. Demo controls and animation are removed, `?demo` URLs return 404, and the legacy `tracking.php` entry redirects to an active trip or the user's rides. Existing booking, pickup/drop-off and carbon history remains saved.

Routing uses the already configured Google provider first, then OSRM (`navigation.osrm_enabled`, `navigation.osrm_url`). OSRM receives only ordered coordinates, never passenger names or account details. Disable it with `NAVIGATION_OSRM_ENABLED=false` or configure a self-hosted endpoint. Routes cache for 30 minutes. Failure produces an explicitly dashed approximate path; a routing failure is never called a road route. The map uses Leaflet and OpenStreetMap tiles already used elsewhere in the app. Road times are estimates, not live ETA guarantees.

The checked-in `tests/fixtures/utem-navigation-road.json` is public road geometry for fictional stops around the application's UTeM coordinates, used by isolated tests. No real user journey appears in that file.

Validation: `php tests/trip_navigation.php` (SQLite memory, array cache, fake HTTP); `node tests/trip_navigation_geometry.cjs`; `node tests/trip_navigation_client.cjs`. `--navigation-preview` generates a labelled, inert live-interface review with synthetic accounts and a static GPS fixture; it does not request device GPS or post real trip changes. Existing ride, appointment, member, carbon and GPS checks remain applicable.

Primary API references: https://leafletjs.com/reference.html and https://project-osrm.org/docs/v5.24.0/api/.
